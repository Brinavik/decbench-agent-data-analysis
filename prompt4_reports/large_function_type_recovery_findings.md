# 大型函数类型恢复规律总结

## 研究范围与证据边界

本研究汇总 DecBench large-function 的 52 个函数、103 个有效 `(LLM, 函数)` 任务的广度裁决，以及 7 个跨项目 case 的源码、两种 LLM 输出、trace 和 Ghidra/IDA 对照追踪。广度扫描中 46/52 个函数（88.5%）至少有一个已归类的 wrong entity，66/103 个任务（64.1%）命中至少一种模式；实体层面为 199/1565（12.7%）wrong、186/1565（11.9%）undeterminable。缺少任务为 `claude-code/shadow/login/main`，因此任务分母固定为 103，函数分母固定为 52。

需要强调，广度扫描的“模式命中”与深度阶段的“人工确认错误”不是同一计数。前者用于估计模式覆盖面，后者用于判定根因；7 个深度 case 是模式覆盖型抽样，不能把 23 条确认错误的比例解释为总体频率。对于每条深度错误，`root_cause` 和 `attribution` 分别回答“为何出现”和“是否为其他工具也会出现的困难”，应当分开阅读。

## 总体规律

第一，复杂结构体布局是最主要的总体缺陷。`LAYOUT-01` 命中 57 个 wrong entity、22/103 个任务（21.4%）和 19/52 个函数（36.5%），是九类模式中函数覆盖率最高的一类。典型路径是模型仅根据当前大函数可见的少量偏移，构造能承载访问的最小结构体，而没有恢复源码的完整字段序列。`cert_parse` 中两种 LLM 都把 22 字段的 `sshkey` 缩为只保留 `type`、`cert` 和 padding/opaque 的视图；`inflate_fast` 中 Claude-code 仅保留 `inflate_state` 的被访问字段。这类输出可能保持局部偏移甚至编译通过，但仍与源码级 type_match 不一致。该结论具有高置信度：广度频率最高，且有两个独立深度 case 的 trace 佐证。它不是不可避免的，Codex 在 `inflate_fast` 及两模型在 `sshkey_cert` 上均可完整恢复布局，说明项目版本类型检索和跨函数证据能显著改善结果。

第二，整数与函数原型是第二优先级的高覆盖错误。`INT-01` 分别命中 20 个任务和 17 个函数（19.4%、32.7%），`FN-01` 为 19 个任务和 17 个函数（18.4%、32.7%）。深度证据显示两条根因并存：二进制中缺少 typedef、signedness 或源码原型信息时，恢复本身不唯一；但模型也会在已有线索下用语义先验重写真实声明。例如 Codex 在 `send_ocsp_request` 中把项目包装函数的 `int ret` 改为 POSIX 风格的 `ssize_t`，并把 `unsigned int headers_size` 改为 `size_t`；Claude-code 在 `check_ea_in_inode` 中把所有调用点均不使用返回值的 `void` 改为 `int`。前者是目前唯一的 Codex 特异证据，后者是两条 Claude-code 特异证据的一部分，均不能直接外推为稳定模型行为；但这两类模式的总体高覆盖率本身证据充分。

第三，限定符和链接属性揭示了“可辨识性上限”与“生成阶段失真”的双重问题。`QUAL-01` 覆盖 10/52 个函数（19.2%），`SC-01` 覆盖 11/52 个函数（21.2%）。在 `wall` 中两 LLM 都丢失参数 `const`，Ghidra/IDA 也未恢复，符合 const 不进入 ABI 的信息缺失。类似地，`cert_parse` 的函数 `static` 与 `send_ocsp_request` 的文件静态 buffer 难以从 stripped 二进制的局部机器码确定。相反，`inflate_fast` 中两种 LLM 已识别 zlib 源函数后仍把 `in/last` 增加 `const`，`cert_parse` 中 Claude-code trace 已写出正确非 const 原型、最终代码却增加 const；这些是可由最终声明一致性检查避免的 LLM 推理/合成缺陷。故不应把所有 qualifier/linkage 不匹配简单归因为模型错误，也不应因为不可见就允许无约束地猜测。

第四，大型函数主要放大实体身份和局部观察问题，而不是自动造成全部类型失败。`inflate_fast` 的长循环中，两模型均把 `code const *here` 改成按值 `code here`，这是跨分支复用和查表重写时“行为等价但实体不等价”的共同失真。`wall` 中 Claude-code 又将栈对齐后的分配量当成 VLA 的逻辑长度；`check_ea_in_inode` 中额外引入 `ret`，破坏了源码实体映射。这些现象支持大型函数复杂性是风险放大器。但 `vipw/main` 和 `get_range` 两个 137 行函数没有确认类型错误，且缺少同项目的小函数对照，因而尚不能证明函数规模具有独立因果效应。此处结论应维持中等置信度。

## 模型共性、模型差异与反例

跨模型共同困难的最强证据来自 `inflate_fast`：两模型同时对 `in/last` 进行 const 化，也都把 `here` 指针按值化；该函数两者 GED 都为 0，type_match 都只有 0.0909。这说明控制流/行为恢复成功不保证源码声明实体恢复成功。该共同现象有中高置信度，但不能据此称所有限定符或指针错误都是 LLM 共性。

Codex 的候选特性是以 API/POSIX 风格先验覆盖项目原型，证据为 `send_ocsp_request` 的 `int -> ssize_t`。Claude Code 的候选特性是最终签名无证据改写和领域类比过扩张，证据为 `check_ea_in_inode` 的 `void -> int` 与标量输出 `-> ea_quota`。两种说法都只能标为初步猜想：Codex 仅有一条深度特异错误，Claude Code 的两条错误均来自同一 case。

反例同样限制结论强度。`vipw/main` 虽然 type_match 为 0.4/0.5，却没有可人工确认的类型/声明错误；`get_range` 的 GED 为 50/43，仍正确恢复五参数签名和核心局部类型。这些 case 证明 type_match、GED 和 byte_match 评价的对象不同，非满 type_match 也不必然等于可解释的类型恢复失败。因此，后续研究不能仅用单一指标替代逐实体审计。

`ST-01` 是需重点复核的低置信度类别。广度扫描显示它覆盖 8 个函数（15.4%），但所选的 7 个深度 case 没有确认的 ST-01；`cert_parse` 的初步结构体冲突经追踪后更准确地归入最小布局问题。`OTHER` 也只有 `check_ea_in_inode` 一个函数中的两条实体语义映射错误。二者均应保留在分类体系中，但不能据此做强机制结论。

## 面向改进的建议

改进工作应优先投入复杂结构体布局和精确项目类型定义恢复。它不仅是发生最广的模式（36.5% 函数），还可能用一个错误影响多个字段和下游表达式。具体应融合跨函数字段偏移、访问宽度、调用关系、精确版本头文件/调试信息；当只获得最小可观察视图时，应明确标为 partial view，而非声称完整源码结构体。

第二优先级是对函数签名和整数类型施加证据约束。应联合调用点、返回值使用、寄存器位宽、符号/零扩展和比较指令做约束求解；项目函数不应因为名称或用途类似 POSIX API 就被替换成 `size_t`、`ssize_t`。在最终 C 生成前，系统应自动检查 trace 中的类型结论与最终声明是否一致，以捕获 `cert_parse` 和 `check_ea_in_inode` 一类“推理已正确、落盘又改错”的缺陷。

第三优先级是对不可恢复信息进行校准。将 ABI 可见类型与源码层的 `static`、`const`、typedef、未访问字段分别报告；对无法唯一判定的项使用 unknown 或候选集，而不是生成确定但不可证的声明。这样既能减少伪精确错误，也能使评测区分信息论限制与可修复推理缺陷。

最后，需扩展实验来验证目前的初步归因：为 Codex/Claude Code 各自的候选特性增加跨项目深度样本；用同项目、同优化级别的小函数作匹配对照以估计 large-function 的独立效应；按模型分层报告模式率及置信区间；并重新深挖 `ST-01` 与 `OTHER` 的分类边界。当前材料足以支持“布局优先，原型/整数其次，信息不可辨识需显式校准”的工程策略，但不足以支持更强的模型优劣或函数规模因果断言。
